## Pattern legend

- **A**: Tone.js native→Tone bridge bug — `nativeNode.connect(toneObj.input)`. Crash. Fix: `Tone.connect(nativeNode, toneObj)`.

- **C**: WaveShaperNode created without `.curve =` assignment — silent passthrough.

- **D**: Mix knob defaults to `0` — installs silent until user moves the knob. Not a bug per se but produces PASSTHROUGH WARNs.

- **E**: Heuristic — no `.connect()` graph path from declared `inputNode` → `outputNode`. Likely silent. False positives possible for compound DSP using channel splitters/mergers/array fan-outs.

- **F**: Conditional `connect()` calls inside `if (...)` blocks — verify the condition is on at install with default params.

- **G**: Missing one of `{ inputNode, outputNode, setParam, dispose }` in the return shape.

## Triage — what's actually a bug

### Pattern A — 0 hits ✅

The earlier `Tone.connect()` patch covered all three native→Tone.PitchShift
sites (pitchForge, pitchLock, voiceForge). The audit confirms no other
factory uses Tone.js (`grep "new Tone\." RecordingStudio.js` matches only
those three), so this class of bug is closed.

### Pattern B — 1 hit (masterWall), NOT a bug

`masterWall` (line 3129) uses `new AudioWorkletNode`, but the factory
wires a Web Audio fallback path **first** (line 3145-3147 in current
file: `input.connect(fbDelay); fbDelay.connect(fbLim); fbLim.connect(output);`),
then attempts the worklet asynchronously and swaps over only if the
worklet load succeeds (`ensureWorklet.then((ok) => { if (!ok) return; ... }`).
Either path produces audio. No fix needed.

### Pattern C — 0 hits ✅

Every `createWaveShaper()` is followed by a `.curve = ...` assignment.

### Pattern D — 23 hits, INTENTIONAL design (mix knob = 0 for sends)

These are reverbs / delays / modulation effects where `mix=0` is the
expected install-time default — the user dials it in. Comparable to
opening a Pro Tools reverb at 0% wet on an insert.

The `verifyPluginProcessesAudio` instrumentation will log `PASSTHROUGH
WARN` for these on first install (output is silent because `wet.gain=0`),
but that's a false alarm in the diagnostic, not a plugin bug. The user
moving the mix knob > 0 makes them audible.

**Optional UX improvement (NOT a bug fix):** change `PLUGIN_DEFAULTS.mix`
from `0` to `25` in `src/front/js/component/SPXPlugins.js` for
insert-style plugins, plus `REVERB_BASE_DEFAULTS.mix: 0 → 25` at line
1873. Would mean users hear the effect immediately on insert. Defer
this — it's a UX call, not a correctness one, and changes the audible
behavior for every existing user who's used to mix=0.

### Pattern E — 6 hits, all FALSE POSITIVES

The audit's static graph reachability misses two valid wiring patterns:

1. **Loop-variable rebinding** (`spectraCurve`, `graphicEQ`,
   `vocoderSPX`): `let prev = head; for (const f of filters) {
   prev.connect(f); prev = f; } prev.connect(tail);` — the regex
   captures `prev.connect(tail)` as `prev → tail` rather than
   `lastFilter → tail`, so `head → tail` is never inferred.
2. **forEach-with-property-access** (`hall`, `plate`, `spring`):
   `combs.forEach(c => { pre.connect(c.d); c.d.connect(sum); });` —
   the regex sees `pre → c` (loop variable, not a real node) and
   `sum.connect(...)`, but doesn't realize the `c.d` graph is connected
   through the loop body.

I verified `hall` (line 4096-4119) and `spectraCurve` (line 3679-3691)
manually — both have valid input→output paths via the loop body. The
heuristic just can't model variable rebinding without an AST parser.

### Pattern F — 0 hits ✅

No conditional `if (...) { x.connect(y); }` blocks at install time.
(The `if (gated > 0) { ps.connect(g); }` in voiceForge is intentional
CPU saving — voice gain at 0 → don't wire ps→g — and is updated when
the user enables a voice via setVoiceConnected.)

### Pattern G — 0 hits ✅

All 102 factories return `{ inputNode, outputNode, setParam, dispose }`.

## Bottom-line conclusion

**The systemic audit finds no remaining code bugs requiring a fix.**
F4-C-FIX's earlier `Tone.connect` patch closed Pattern A; everything
else surfaces as either intentional design (Pattern D send-mix
defaults) or false positives from a static heuristic that can't model
loop-variable rebinding (Pattern E).

The defensive instrumentation (chainer guards, `verifyPluginProcessesAudio`,
expanded error logs) stays in place as runtime safety net for any
future regression.

**Recommended next step:** user runs the broad smoke test from the
prior turn (add ~2-3 plugins from each category, press Play) to
confirm nothing else throws. Plugins that hit Pattern D will log
`[F4-C-FIX] PASSTHROUGH WARN` on first install — that's expected and
goes away once the mix knob is moved. Any *unexpected*
`[F4-C-FIX] factory threw` is a new bug; paste the stack and we patch.

If the user wants the UX nicety of insert-time audible reverbs/delays,
that's a separate, deliberate change to `PLUGIN_DEFAULTS` rather than
factory code.
